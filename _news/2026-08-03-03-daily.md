## 1. "부모가 리렌더링되면 자식도 무조건 리렌더링된다"는 것부터

리액트 성능 최적화 기법을 이해하려면 먼저 기본 동작을 알아야 한다: **부모 컴포넌트가 리렌더링되면, props가 하나도 안 바뀌었어도 자식은 기본적으로 전부 리렌더링된다.**

```jsx
function Parent() {
  const [count, setCount] = useState(0);
  return (
    <div>
      <button onClick={() => setCount(c => c + 1)}>{count}</button>
      <ExpensiveChild /> {/* props 없음, 그런데도 매번 리렌더링됨 */}
    </div>
  );
}
```

`ExpensiveChild`는 어떤 props도 받지 않는데도, `count`가 바뀌어 `Parent`가 리렌더링될 때마다 함께 다시 렌더링된다. 이게 "리렌더링 = 함수 재실행"일 뿐 "리렌더링 = DOM 변경"은 아니라서(디핑 결과 변경 없으면 DOM은 그대로) 눈에 보이는 문제는 없을 수 있지만, `ExpensiveChild` 내부에 무거운 연산이 있다면 그 연산이 매번 다시 돈다.

## 2. React.memo — 얕은 비교로 리렌더링 자체를 스킵

```jsx
const ExpensiveChild = React.memo(function ExpensiveChild({ data }) {
  console.log("렌더링");
  return <div>{heavyCompute(data)}</div>;
});
```

`React.memo`는 이전 props와 새 props를 **얕은 비교(shallow compare)**해서, 모두 같으면 컴포넌트 함수 자체를 재실행하지 않고 이전 렌더 결과를 그대로 재사용한다.

여기서 함정은 "얕은 비교"다.

```jsx
function Parent() {
  const [count, setCount] = useState(0);
  return <ExpensiveChild data={{ value: 1 }} />; // 매 렌더마다 새 객체!
}
```

`{ value: 1 }`은 매번 새로 생성되는 객체라서, 내용이 같아도 참조가 달라 얕은 비교에서 "다르다"고 판정된다. 즉 `React.memo`를 씌워도 이 경우엔 매번 리렌더링된다. 원시값(문자열, 숫자)이나 참조가 고정된 값을 props로 넘길 때만 `React.memo`가 제 역할을 한다.

## 3. children 속성을 이용한 리렌더링 방지 — memo보다 근본적인 해법

`React.memo`는 "얕은 비교"라는 한계가 있지만, **`children`을 props로 받는 패턴**은 아예 다른 방식으로 리렌더링을 막는다.

```jsx
function Parent({ children }) {
  const [count, setCount] = useState(0);
  return (
    <div>
      <button onClick={() => setCount(c => c + 1)}>{count}</button>
      {children}
    </div>
  );
}

function App() {
  return (
    <Parent>
      <ExpensiveChild /> {/* Parent 리렌더링과 무관하게 리렌더링 안 됨 */}
    </Parent>
  );
}
```

핵심은 `<ExpensiveChild />`가 **`Parent` 내부가 아니라 `App`에서 생성된다**는 점이다. `Parent`가 `count` 때문에 리렌더링될 때, `Parent` 함수는 다시 실행되지만 `children`이라는 props 자체는 `App`이 리렌더링되지 않는 한 새로 생성되지 않는다. 즉 `children`으로 전달된 엘리먼트는 **참조가 그대로 유지**되고, 리액트는 "이 자식 엘리먼트, 이전과 같은 참조네"라고 판단해서 `ExpensiveChild`를 재실행하지 않는다.

이 패턴이 `React.memo`보다 근본적인 이유는, props 비교 로직에 의존하지 않고 애초에 "새로운 엘리먼트가 생성되지 않는" 구조를 만들기 때문이다. `memo`는 "비교해서 건너뛰기"고, `children` 패턴은 "애초에 다시 만들지 않기"다. 레이아웃/컨테이너 컴포넌트(사이드바, 모달 래퍼 등)에서 상태를 가지면서 무거운 자식을 감싸는 경우 자주 쓰인다.

## 4. useMemo — 계산 결과를 캐싱

```jsx
function ProductList({ products, filterText }) {
  const filtered = useMemo(() => {
    console.log("필터링 연산 실행");
    return products.filter(p => p.name.includes(filterText));
  }, [products, filterText]);

  return <ul>{filtered.map(p => <li key={p.id}>{p.name}</li>)}</ul>;
}
```

의존성 배열(`[products, filterText]`)이 바뀌지 않으면, 리렌더링이 일어나도 `useMemo` 안의 함수를 다시 실행하지 않고 이전에 계산해둔 값을 그대로 반환한다. 리스트 필터링·정렬처럼 연산 비용이 큰 로직에 유용하다.

주의할 점은 `useMemo`도 **의존성 배열 자체가 얕은 비교**라는 것. `products`가 매 렌더마다 새 배열로 만들어지는 코드라면(`.map()`, `.filter()`로 매번 새로 생성 등) 캐싱 효과가 없다. 그리고 계산이 가벼운 값에 `useMemo`를 씌우면, 메모이제이션 자체의 오버헤드(의존성 비교, 메모리 유지)가 이득보다 커질 수 있어서 "일단 다 씌우고 보자"는 안티패턴이다.

## 5. useCallback — 함수 참조를 고정

```jsx
function Parent() {
  const [count, setCount] = useState(0);

  const handleClick = useCallback(() => {
    console.log("클릭");
  }, []); // 의존성 없음 → 참조 항상 동일

  return (
    <div>
      <span>{count}</span>
      <MemoChild onClick={handleClick} />
    </div>
  );
}

const MemoChild = React.memo(function MemoChild({ onClick }) {
  console.log("MemoChild 렌더링");
  return <button onClick={onClick}>클릭</button>;
});
```

`useCallback` 없이 `handleClick`을 그냥 함수로 선언하면, `Parent`가 리렌더링될 때마다 새 함수 객체가 만들어진다. `MemoChild`가 `React.memo`로 감싸져 있어도, `onClick` props의 참조가 매번 달라지므로 얕은 비교에서 "다르다"고 판정되어 memo가 무력화된다. `useCallback`으로 함수 참조를 고정하면 이 문제가 해결된다.

즉 `useCallback`은 그 자체로 성능 최적화가 아니라, **`React.memo`가 제대로 동작하도록 돕는 보조 도구**다. 자식이 `memo`로 감싸져 있지 않다면 `useCallback`을 아무리 써도 자식은 어차피 리렌더링되므로 의미가 없다.

## 6. 세 기법을 언제 쓸지

- **`children` 패턴**: 상태를 가진 컨테이너가 무거운 자식을 감쌀 때. 가장 근본적이고 부작용이 적어서 우선적으로 고려.
- **`React.memo`**: 자식이 원시값 위주 props를 받고, 부모가 자주 리렌더링되는 리스트 아이템 등.
- **`useMemo`**: 연산 비용이 실제로 큰 값(대량 배열 필터/정렬, 복잡한 계산)에만.
- **`useCallback`**: `memo`로 감싼 자식에게 함수를 props로 넘길 때만 의미 있음. 단독으로는 효과 없음.

## 정리 표

| 기법 | 막는 대상 | 전제 조건 | 흔한 실수 |
|---|---|---|---|
| React.memo | 컴포넌트 재실행 | props가 얕은 비교로 동일해야 함 | 매번 새 객체/배열을 props로 넘김 |
| children 패턴 | 컴포넌트 재실행 | 자식 엘리먼트를 상위에서 생성해 전달 | 상태를 가진 컴포넌트 내부에서 자식을 직접 JSX로 작성 |
| useMemo | 값 재계산 | 의존성 배열이 얕은 비교로 동일 | 가벼운 연산에 남용, 의존성 배열 실수 |
| useCallback | 함수 참조 변경 | 자식이 React.memo로 감싸져 있어야 효과 있음 | memo 없는 자식에 사용 (무의미) |

### TypeScript 프로젝트에서의 참고

`React.memo`에 제네릭 컴포넌트를 씌우면 타입 추론이 깨지는 경우가 있다 (`memo`의 반환 타입이 제네릭을 지워버림). 이럴 땐 함수 선언에 타입 단언을 걸거나, `memo`를 감싸는 커스텀 헬퍼 타입을 만들어 쓰는 게 흔한 우회법이다. 또한 `useCallback`/`useMemo`의 의존성 배열은 `eslint-plugin-react-hooks`의 `exhaustive-deps` 규칙을 반드시 켜두는 게 좋다 — TS는 배열 안에 빠진 의존성을 타입 에러로 잡아주지 않기 때문에, 이 부분은 린트 규칙에 의존해야 한다.
