## 1. "어차피 런타임엔 다 지워지는데" 라는 질문

TypeScript는 컴파일하면 타입이 전부 지워지고 결국 JS가 실행된다. 그럼 "런타임 버그를 막아주는 것도 아닌데 왜 굳이 써야 하나"라는 질문이 나올 수 있다. 답은 "런타임 이전, 즉 개발 시점에 잡을 수 있는 오류의 범위가 완전히 다르다"는 것이다. 오늘은 그 이유를 실제 코드 예시로 정리했다.

---

## 2. 컴파일 타임에 잡히는 것 vs 안 잡히는 것

```js
// JS
function getUser(id) {
  return fetch(`/api/users/${id}`).then(res => res.json());
}

getUser("abc").then(user => {
  console.log(user.name.toUpperCase()); // user가 null이면? name이 undefined면?
});
```

JS에서는 `user`가 `null`이든, `name`이 없든 실행 전까지 아무것도 알 수 없다. 배포 후 프로덕션에서 에러 로그를 보고서야 안다.

```ts
// TS
interface User {
  id: string;
  name: string | null;
}

async function getUser(id: string): Promise<User> {
  const res = await fetch(`/api/users/${id}`);
  return res.json();
}

const user = await getUser("abc");
console.log(user.name.toUpperCase());
// Error: Object is possibly 'null'.
```

`name`이 `string | null`이라고 명시하는 순간, `.toUpperCase()`를 호출하려는 시점에 컴파일러가 "null일 수도 있는데 처리 안 했다"고 즉시 알려준다. 이 오류는 **코드를 실행하지 않아도**, 에디터에서 타이핑하는 즉시 잡힌다.

## 3. 리팩터링 안전망

```ts
interface Order {
  id: string;
  totalPrice: number;
}

function formatOrder(order: Order) {
  return `#${order.id}: $${order.totalPrice}`;
}
```

여기서 `totalPrice`를 `total`로 이름을 바꾼다고 하자. JS였다면 `formatOrder` 안의 `order.totalPrice`는 그냥 `undefined`가 되고, `$undefined`라는 문자열이 조용히 만들어진다. 프로덕션에 배포되고 나서야 발견될 수도 있다.

TS에서는 `Order` 인터페이스의 필드명을 바꾸는 순간, 이 필드를 참조하는 모든 곳에서 컴파일 에러가 뜬다. 에디터가 "여기, 여기, 여기 다 고쳐야 해"라고 파일 몇 개, 몇 번째 줄인지까지 알려준다. 이게 흔히 말하는 "타입이 곧 리팩터링 안전망"이라는 것의 실체다. 사람이 grep으로 찾아 고치는 게 아니라 컴파일러가 빠짐없이 찾아준다.

## 4. 협업에서의 이점 — 타입이 곧 문서

```ts
interface FetchUsersOptions {
  page: number;
  pageSize: number;
  sortBy?: "name" | "createdAt";
  order?: "asc" | "desc";
}

function fetchUsers(options: FetchUsersOptions): Promise<User[]> { /* ... */ }
```

이 함수를 처음 보는 팀원은 함수 본문을 읽지 않고도 시그니처만 보고 "`sortBy`는 `name` 아니면 `createdAt`만 가능하구나", "`page`는 필수, `sortBy`는 선택"이라는 걸 즉시 안다. JS였다면 JSDoc 주석에 의존하거나, 함수 내부 로직을 직접 읽어야 알 수 있었을 정보다. 주석은 코드가 바뀌어도 갱신을 안 하면 거짓말을 하게 되지만, 타입은 코드가 바뀌면 컴파일이 깨지기 때문에 **거짓말을 할 수 없는 문서**다.

## 5. 에디터 지원 — 자동완성이 곧 생산성

타입 정보가 있으면 에디터(VSCode 등)가 정확한 자동완성을 제공한다. `options.` 을 입력하는 순간 `page`, `pageSize`, `sortBy`, `order`만 뜨고 오타가 나면 즉시 빨간 줄이 그어진다. JS에서는 객체 구조를 추론할 방법이 없어서 자동완성이 부정확하거나 아예 안 뜬다. 이 차이는 코드를 "얼마나 빨리 정확하게" 짜는지에 직접적인 영향을 준다.

## 6. 흔한 반박과 그에 대한 답

### "any 쓰면 결국 똑같은 거 아닌가"

```ts
function processData(data: any) {
  return data.value.toUpperCase(); // 타입 체크 무력화
}
```

맞다. `any`를 남발하면 TS의 이점이 전부 사라진다. 하지만 이건 TS의 한계가 아니라 잘못된 사용이다. `any` 대신 `unknown`을 쓰고 타입 가드로 좁혀나가면, "모르는 타입"을 다루면서도 안전성을 유지할 수 있다.

```ts
function processData(data: unknown) {
  if (typeof data === "object" && data !== null && "value" in data) {
    // 여기서부터 안전하게 좁혀진 타입으로 접근
  }
}
```

### "타입 정의하는 시간이 아깝다"

초기 개발 속도는 JS가 약간 빠를 수 있다. 하지만 프로젝트가 커지고 파일 수가 늘어날수록, 타입 없이 리팩터링/디버깅에 드는 시간이 기하급수적으로 늘어난다. 손익분기점은 생각보다 빨리 온다 — 파일이 10개를 넘어가고 팀원이 2명 이상이 되는 순간부터다.

## 정리 표

| 항목 | JS | TS |
|---|---|---|
| null/undefined 접근 오류 | 런타임에 발견 | 컴파일(타이핑) 시점에 발견 |
| 필드명 변경 시 영향 범위 | 수동 grep, 누락 위험 | 컴파일러가 전부 찾아줌 |
| 함수 시그니처 이해 | 본문/주석 의존 | 타입 자체가 문서 |
| 에디터 자동완성 | 부정확/미제공 | 정확한 속성/값 목록 제공 |
| any 남용 시 | - | JS와 사실상 동일 (unknown+가드로 대체 권장) |

### TypeScript 프로젝트에서의 참고

우리 팀 프로젝트처럼 프론트-백엔드를 모두 TS로 작성하면 얻는 추가 이점이 하나 더 있다. API 응답 타입을 백엔드와 공유(모노레포의 공용 패키지, 또는 `zod`/`tRPC`로 스키마를 한 곳에서 관리)하면, 백엔드가 필드를 바꿨을 때 프론트 컴파일이 즉시 깨져서 "API 스펙 불일치"를 배포 전에 잡을 수 있다. REST + 수동 타입 유지보수보다 `tRPC`나 OpenAPI 코드 생성기를 붙여 타입을 자동 동기화하는 방향이 장기적으로 훨씬 안전하다.
