상태를 뭉뚱그리지 않기 — 앱 하나에 상태가 몇 종류나 섞여 있을까

Created on August 05, 2026

2026   ·   TypeScript   React   State Management   MobX   TanStack Query   Zustand

“상태관리 라이브러리 뭐 쓸까”는 프론트엔드에서 제일 자주 나오는 질문이지만, 사실 이 질문 자체가 함정이다. 앱 안의 “상태”는 하나의 덩어리가 아니라 성격이 완전히 다른 여러 종류가 섞여 있고, 그걸 구분하지 않은 채 Redux든 MobX든 하나의 도구에 전부 밀어넣으면 캐싱·동기화·URL 연동 같은 걸 전부 직접 구현하게 된다. 이 글은 상태를 종류별로 쪼개고, 각 종류에 어떤 도구가 왜 어울리는지, 그리고 같은 기능을 여러 상태관리 스택(Redux Toolkit, RTK Query, TanStack Query, MobX, Zustand)으로 구현했을 때 코드가 어떻게 달라지는지를 설문 앱 예제로 정리한다.

1. “상태관리 뭐 쓸까”라는 질문이 틀린 이유

라이브러리를 고르기 전에 먼저 물어야 할 건 “이 값의 진실(source of truth)이 어디에 있는가”다. 이 기준 하나로 상태는 최소 일곱 갈래로 나뉜다.

  1. 서버 상태 (Server State) — DB에 있는 데이터, fetch 필요
  2. 전역 클라이언트 상태 (Global UI State) — 여러 컴포넌트가 공유하는 UI 값
  3. 로컬 컴포넌트 상태 (Local State) — 그 컴포넌트 안에서만 의미 있는 값
  4. 폼 상태 (Form State) — 입력값, 검증 에러, 제출 여부
  5. URL 상태 (URL State) — 쿼리스트링/경로에 들어있는 값
  6. 영속 상태 (Persisted State) — 브라우저를 닫아도 유지돼야 하는 값
  7. 낙관적 업데이트 (Optimistic State) — 서버 응답 전에 미리 반영하고 실패 시 롤백

이 중 “상태관리 라이브러리”라는 이름으로 보통 떠올리는 Redux/MobX/Zustand는 사실 2번(전역 클라이언트 상태)만을 위한 도구다. 나머지는 각자 전용 도구가 따로 있고, 그 전용 도구를 안 쓰면 결국 그 라이브러리 위에 로딩·에러·재검증·URL 동기화를 직접 재구현하게 된다.

2. 판별 기준을 표로 정리하면

질문 Yes면 No면
새로고침 후 서버에 다시 물어봐도 같은 값이 나오나 서버 상태 클라이언트 상태
다른 사용자도 똑같이 볼 수 있는 값인가 서버 상태 클라이언트 상태
“오래된 값”이라는 개념이 있어 재요청이 필요한가 서버 상태 클라이언트 상태
링크로 공유되거나 뒤로가기와 연동돼야 하는가 URL 상태 그 외
탭을 닫아도 유지돼야 하는가 영속 상태 휘발성 상태

이 판별을 실제 설문 앱에 적용하면 다음과 같이 갈린다.

값 종류 이유
설문 목록, 설문 상세, 응답 통계 서버 상태 DB가 원본, 다른 사용자도 같은 값을 봄
로그인한 사용자의 role 서버 상태 서버 세션이 원본
수정 모달 열림 여부 전역 클라이언트 상태 화면을 벗어나면 의미 없음
작성 중인 설문 응답 입력값 폼 상태 검증·제출과 강하게 결합
목록 필터/정렬/페이지 URL 상태 링크 공유·새로고침 유지 필요
다크모드 설정 영속 상태 탭을 닫아도 유지돼야 함
좋아요/북마크 토글 낙관적 업데이트 응답 지연 없이 즉시 피드백 필요

3. 서버 상태를 전역 상태 도구에 직접 넣으면 뭐가 힘들어지는가

MobX로 서버 상태까지 관리하면 이런 코드가 나온다.

class SurveyStore {
  items: Survey[] = [];
  isLoading = false;
  error: string | null = null;

  constructor() {
    makeAutoObservable(this, {}, { autoBind: true });
  }

  async fetchSurveys() {
    this.isLoading = true;
    try {
      const res = await fetch('/api/surveys');
      this.items = await res.json();
    } catch (e) {
      this.error = String(e);
    } finally {
      this.isLoading = false;
    }
  }
}

이 코드 자체는 문제없이 동작한다. 문제는 요구사항이 하나씩 늘어날 때다. “같은 데이터를 두 화면에서 동시에 요청하면 중복 fetch를 막아야 한다”, “5분이 지나면 백그라운드에서 자동으로 재검증해야 한다”, “다른 화면에서 설문을 수정하면 이 목록도 갱신돼야 한다” — 이런 요구가 하나씩 붙을 때마다 isLoading/error/lastFetchedAt/isStale 같은 필드와 그걸 다루는 로직을 계속 손으로 늘려야 한다. TanStack Query나 RTK Query는 이걸 이미 다 구현해둔 라이브러리라, 서버 상태에는 이쪽을 쓰는 게 실무 표준으로 자리잡은 이유가 여기에 있다.

function useSurveys() {
  return useQuery({
    queryKey: ['surveys'],
    queryFn: () => fetch('/api/surveys').then((res) => res.json()),
    staleTime: 5 * 60 * 1000, // 5분 후 자동 재검증
  });
}

같은 기능을 훨씬 적은 코드로, 그리고 캐시 무효화·중복 요청 방지까지 포함해서 얻는다.

4. 스택별로 같은 기능을 짜보면 코드량과 책임이 어떻게 갈리는가

설문 목록 조회 + 설문 생성 + 모달 상태라는 동일한 기능을, 서버 상태와 클라이언트 상태를 어떻게 나누는지 기준으로 다섯 스택에 대입해봤다.

Redux Toolkit (RTK, RTK Query 없이 순수 버전)

export const fetchSurveys = createAsyncThunk('surveys/fetch', async () => {
  const res = await fetch('/api/surveys');
  return res.json();
});

const surveySlice = createSlice({
  name: 'surveys',
  initialState: { items: [], isLoading: false, error: null as string | null },
  reducers: {},
  extraReducers: (builder) => {
    builder
      .addCase(fetchSurveys.pending, (state) => { state.isLoading = true; })
      .addCase(fetchSurveys.fulfilled, (state, action) => {
        state.items = action.payload;
        state.isLoading = false;
      })
      .addCase(fetchSurveys.rejected, (state, action) => {
        state.error = action.error.message ?? null;
        state.isLoading = false;
      });
  },
});

서버 상태를 순수 RTK로 다루면 로딩/에러/성공 3단계를 매번 직접 분기해야 한다. 대신 Redux DevTools에서 액션이 시간순으로 전부 기록되기 때문에 “언제 무슨 일이 일어났는지” 추적하는 디버깅 경험은 가장 강력하다.

RTK Query (서버 상태 전용, RTK 안에 내장)

export const surveyApi = createApi({
  reducerPath: 'surveyApi',
  baseQuery: fetchBaseQuery({ baseUrl: '/api' }),
  tagTypes: ['Survey'],
  endpoints: (builder) => ({
    getSurveys: builder.query<Survey[], void>({
      query: () => 'surveys',
      providesTags: ['Survey'],
    }),
    createSurvey: builder.mutation<Survey, Partial<Survey>>({
      query: (body) => ({ url: 'surveys', method: 'POST', body }),
      invalidatesTags: ['Survey'], // 생성 성공 시 목록 자동 재조회
    }),
  }),
});

invalidatesTags/providesTags로 “이 데이터가 바뀌면 저 쿼리를 다시 가져와라”는 관계를 선언적으로 표현한다. 위에서 손으로 짰던 pending/fulfilled/rejected 분기가 통째로 사라진다.

TanStack Query + Zustand (서버/클라이언트를 완전히 분리하는 조합)

// 서버 상태
function useSurveys() {
  return useQuery({
    queryKey: ['surveys'],
    queryFn: () => fetch('/api/surveys').then((res) => res.json()),
  });
}

function useCreateSurvey() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: (data: Partial<Survey>) =>
      fetch('/api/surveys', { method: 'POST', body: JSON.stringify(data) }),
    onSuccess: () => queryClient.invalidateQueries({ queryKey: ['surveys'] }),
  });
}

// 클라이언트 상태
export const useUiStore = create<{ isModalOpen: boolean; toggleModal: () => void }>((set) => ({
  isModalOpen: false,
  toggleModal: () => set((s) => ({ isModalOpen: !s.isModalOpen })),
}));

서버 상태 코드에 로딩/에러/캐시 관련 필드가 아예 등장하지 않는다는 게 RTK 순수 버전과의 가장 큰 차이다. 클라이언트 상태(isModalOpen)는 서버 상태와 완전히 분리된 별도 스토어에만 존재해서, “이 값이 서버 값인지 UI 값인지” 헷갈릴 여지가 코드 구조상 사라진다. 2026년 현재 실무에서 가장 널리 쓰이는 조합이 이 형태다.

MobX (서버 상태까지 클래스로 직접 관리)

class SurveyStore {
  items: Survey[] = [];
  isLoading = false;

  constructor() {
    makeAutoObservable(this, {}, { autoBind: true });
  }

  async fetchSurveys() {
    this.isLoading = true;
    const res = await fetch('/api/surveys');
    this.items = await res.json();
    this.isLoading = false;
  }

  async createSurvey(data: Partial<Survey>) {
    await fetch('/api/surveys', { method: 'POST', body: JSON.stringify(data) });
    await this.fetchSurveys();
  }
}

서버/클라이언트 상태를 같은 클래스 패턴으로 다룰 수 있다는 일관성이 장점이지만, 캐시 무효화와 중복 요청 방지는 여전히 직접 구현해야 한다. TanStack Query와 병행해서 “MobX는 UI 상태만, 서버 상태는 TanStack Query”로 역할을 나누는 조합도 실무에서 흔히 쓰인다.

Zustand (서버 상태까지 스토어로 직접 관리)

export const useSurveyStore = create<SurveyState>((set, get) => ({
  items: [],
  isLoading: false,
  fetchSurveys: async () => {
    set({ isLoading: true });
    const res = await fetch('/api/surveys');
    set({ items: await res.json(), isLoading: false });
  },
  createSurvey: async (data) => {
    await fetch('/api/surveys', { method: 'POST', body: JSON.stringify(data) });
    await get().fetchSurveys();
  },
}));

MobX와 결이 비슷하지만 클래스 없이 함수형 클로저로 짠다는 차이만 있고, 서버 상태를 직접 다룰 때의 한계(캐싱/재검증 미구현)는 동일하게 남는다.

5. 놓치기 쉬운 두 종류 — 폼 상태와 URL 상태

지금까지의 다섯 스택 비교는 전부 “전역 클라이언트 상태 vs 서버 상태” 축에 머물러 있는데, 실무에서 실수가 가장 잦은 건 오히려 폼 상태와 URL 상태를 이 축 안에 억지로 넣는 경우다.

폼 상태를 MobX/Zustand 스토어에 넣으면, 인풋 하나 바뀔 때마다 전역 상태가 갱신되면서 그 스토어를 구독하는 다른 컴포넌트까지 불필요하게 리렌더링될 수 있다. react-hook-form처럼 비제어 방식(ref 기반)으로 입력을 다루는 폼 전용 라이브러리를 쓰면 이 문제 자체가 생기지 않는다.

const { register, handleSubmit } = useForm<SurveyForm>();
// register된 인풋은 전역 상태를 거치지 않고 리렌더링 최소화

URL 상태를 전역 스토어에 넣으면 “새로고침하면 필터가 초기화된다”, “이 목록 링크를 복사해서 보내도 필터가 안 걸린 상태로 열린다” 같은 문제가 생긴다. 필터/정렬/페이지 값은 useSearchParams로 주소창에 반영해야 뒤로가기, 새로고침, 링크 공유가 전부 자연스럽게 동작한다.

const [searchParams, setSearchParams] = useSearchParams();
const page = Number(searchParams.get('page') ?? '1');

6. 결론 — 도구가 아니라 상태의 종류부터 나눈다

“Redux냐 MobX냐 Zustand냐”라는 질문은 사실 상태의 7종류 중 딱 하나(전역 클라이언트 상태)에만 해당하는 질문이다. 서버 상태는 TanStack Query/RTK Query 같은 전용 도구, 폼 상태는 react-hook-form, URL 상태는 라우터의 쿼리스트링 API, 영속 상태는 persist 미들웨어나 직접적인 storage 연동으로 각각 분리하는 게 먼저다. 그렇게 역할을 나눠놓고 나면, 남는 “진짜 전역 클라이언트 상태”는 생각보다 양이 많지 않고, 그 좁아진 범위 안에서는 MobX든 Zustand든 Redux Toolkit이든 어느 걸 골라도 큰 차이가 없어진다. 즉 상태관리 스택 선택 고민의 8할은 “상태를 종류별로 먼저 쪼갰는가”에서 이미 끝나 있다.

정리 표

상태 종류 예시 특징 전용 도구
서버 상태 설문 목록, 사용자 role fetch 필요, staleness 존재, 여러 사용자 공유 TanStack Query, RTK Query
전역 클라이언트 상태 모달 열림, 다크모드 토글 화면 여러 곳에서 공유, 서버와 무관 MobX, Zustand, Redux Toolkit
로컬 컴포넌트 상태 아코디언 펼침, hover 해당 컴포넌트 밖에서 의미 없음 useState
폼 상태 입력값, 검증 에러 입력마다 빈번히 갱신, 검증 로직 결합 react-hook-form
URL 상태 검색어, 페이지, 필터 공유·새로고침·뒤로가기와 연동 필요 useSearchParams
영속 상태 로그인 토큰, 설정값 탭을 닫아도 유지 localStorage + persist 미들웨어
낙관적 업데이트 좋아요, 순서 변경 응답 전 선반영, 실패 시 롤백 TanStack Query optimistic update

다음 단계로 갈 수 있는 방향

지금 정리는 “상태를 종류별로 나눈다”는 원칙 수준이고, 실제로 다섯 스택으로 동일한 설문 앱을 완성해보면 여기서 더 세부적인 차이가 드러날 것 같다. RTK Query의 태그 기반 캐시 무효화가 실제로 몇 줄이나 코드를 줄여주는지, TanStack Query의 staleTime/gcTime 튜닝이 네트워크 요청 수에 실제로 얼마나 영향을 주는지, MobX의 자동 추적이 Zustand의 수동 선택자(selector) 방식보다 실제 리렌더링 횟수를 얼마나 줄이는지를 다음 글에서 각 스택별로 프로파일링해볼 계획이다. 상태관리는 “정답 하나를 고르는 문제”가 아니라 “이 값의 성격에 맞는 도구를 각각 배치하는 설계 문제”라는 게, 이번에 다섯 스택을 나란히 놓고 비교하며 다시 확인한 지점이다.
