1. 리액트의 특징을 다시 정리해야 했던 이유

“리액트는 단방향 데이터 흐름이다”, “state가 바뀌면 리렌더링된다” 정도는 누구나 말할 수 있는데, 막상 “왜 단방향이어야 하는가”, “리렌더링과 실제 DOM 업데이트는 같은 타이밍인가”를 물으면 설명이 막힌다. 오늘은 이 부분을 순서대로 정리했다.

왜 단방향 데이터 흐름인가

function Parent() {
  const [count, setCount] = useState(0);
  return <Child count={count} onIncrement={() => setCount(c => c + 1)} />;
}

function Child({ count, onIncrement }) {
  return <button onClick={onIncrement}>{count}</button>;
}

데이터는 항상 부모 → 자식으로 props를 통해서만 내려간다. 자식이 부모의 state를 직접 바꿀 방법은 없고, 오직 부모가 넘겨준 콜백(onIncrement)을 호출해서 “변경을 요청”할 뿐이다.

양방향 바인딩(Angular의 ngModel, Vue의 v-model)과 비교하면 차이가 명확하다. 양방향에서는 자식이 값을 바꾸면 부모도 자동으로 바뀌는데, 컴포넌트 트리가 깊어지면 “어디서 값이 바뀌었는지” 추적이 어려워진다. 단방향은 항상 최상위에서 아래로만 흐르기 때문에, 버그가 생겼을 때 “이 state를 소유한 곳”까지만 거슬러 올라가면 원인을 찾을 수 있다. 데이터 흐름이 예측 가능해지는 대신, 상태를 바꾸려면 반드시 콜백을 거쳐야 하는 보일러플레이트가 생긴다.

2. 상태 관리 — state는 언제, 어디서 죽는가

리액트의 상태 관리를 이해할 때 가장 먼저 헷갈리는 건 “state가 컴포넌트 함수에 저장되는 게 아니다”라는 점이다.

function Counter() {
  const [count, setCount] = useState(0); // 매 렌더마다 이 줄이 다시 실행된다
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}

Counter 함수는 렌더링될 때마다 처음부터 다시 실행되는 일반 함수다. 그런데 count는 유지된다. 왜냐하면 useState가 반환하는 값은 함수 내부 변수가 아니라, 리액트가 파이버(Fiber) 노드에 별도로 저장해두는 값이기 때문이다. 함수 컴포넌트는 매번 새로 실행되지만, 그 함수가 몇 번째 파이버에 속하는지는 리액트가 관리하고, useState는 그 파이버에 연결된 훅 리스트에서 순서대로 값을 꺼내온다. (그래서 훅을 조건문 안에서 호출하면 안 된다 — 순서가 어긋나는 순간 엉뚱한 값을 꺼내오게 된다.)

state가 사라지는 시점은 “컴포넌트가 언마운트될 때”다. 같은 위치에 다른 컴포넌트가 렌더되거나, 부모가 key를 바꿔서 강제로 새 인스턴스를 만들면 그 순간 파이버가 폐기되고 state도 함께 사라진다. 반대로 부모가 리렌더링되어도 같은 위치에 같은 컴포넌트가 그대로 있으면 파이버가 재사용되고 state는 유지된다.

3. 렌더 페이즈 vs 커밋 페이즈

리액트의 렌더링은 사실 두 단계로 나뉜다.

(1) 렌더 페이즈 (Render Phase)

  • 컴포넌트 함수를 호출해서 새로운 JSX(엘리먼트 트리)를 계산한다.
  • 이전 트리와 비교(diffing)해서 어떤 변경이 필요한지 계산한다.
  • 이 단계에서는 실제 DOM을 건드리지 않는다. 순수하게 “무엇이 바뀌어야 하는지” 계산만 한다.
  • 이 단계는 중단되고 재시작될 수 있다. Concurrent 모드에서는 더 우선순위 높은 업데이트가 들어오면 렌더 페이즈를 버리고 다시 시작하기도 한다. 그래서 렌더 페이즈에 부수효과(side effect)를 넣으면 안 된다 — 여러 번 실행될 수 있기 때문이다.

(2) 커밋 페이즈 (Commit Phase)

  • 렌더 페이즈에서 계산된 변경사항을 실제 DOM에 반영한다.
  • useLayoutEffect가 DOM 변경 직후, 브라우저 페인트 전에 동기적으로 실행된다.
  • 그 다음 브라우저가 화면을 그리고, useEffect가 비동기로 실행된다.
  • 커밋 페이즈는 한 번 시작하면 중단되지 않는다. 일관성이 깨진 화면을 사용자에게 보여줄 수 없기 때문이다.
렌더 페이즈 (중단 가능, 여러 번 실행될 수 있음)
   ↓
커밋 페이즈 (DOM 변경 + useLayoutEffect, 중단 불가)
   ↓
브라우저 페인트
   ↓
useEffect 실행

이 구분이 중요한 이유는, “렌더링됐다”와 “화면에 반영됐다”가 다른 타이밍이라는 걸 알아야 useEffect/useLayoutEffect의 차이, 그리고 Concurrent 렌더링에서의 “렌더는 여러 번 될 수 있다”는 동작을 이해할 수 있기 때문이다.

4. 리콘실리에이션, 디핑, 휴리스틱 알고리즘

리액트가 “가상 DOM과 실제 DOM을 비교해서 최소한만 바꾼다”고 할 때, 그 비교 과정이 리콘실리에이션(Reconciliation)이고, 실제로 두 트리를 비교하는 알고리즘이 디핑(Diffing)이다.

트리 두 개를 완전히 정확하게 비교하는 알고리즘(minimum edit distance)은 O(n³) 복잡도를 가진다. 노드 수천 개짜리 UI 트리에 이걸 그대로 적용하면 성능이 나오지 않는다. 그래서 리액트는 실용적인 휴리스틱(heuristic) 규칙 두 가지를 세우고, 그 안에서만 비교한다.

휴리스틱 규칙 1 — 타입이 다르면 서브트리를 통째로 버린다

// 이전
<div><Counter /></div>
// 이후
<span><Counter /></span>

div가 span으로 바뀌면, 리액트는 내부에 있던 Counter가 실질적으로 같은 컴포넌트인지 확인하지 않는다. 최상위 타입이 다르므로 이전 트리 전체를 언마운트하고 새 트리를 처음부터 마운트한다. Counter의 state는 그대로 날아간다.

휴리스틱 규칙 2 — key로 리스트 아이템의 정체성을 판단한다

{items.map(item => <li key={item.id}>{item.text}</li>)}

key가 없으면 리액트는 배열 인덱스로 대응시키는데, 중간에 아이템이 삽입/삭제되면 인덱스가 밀리면서 엉뚱한 DOM 노드에 엉뚱한 state가 매칭되는 문제가 생긴다. key를 안정적인 id로 주면, 리액트는 “이 항목은 이전의 그 항목과 같다”고 정확히 판단하고 DOM 노드를 재사용한다.

이 두 규칙 덕분에 O(n³) 문제가 O(n)으로 줄어든다. 대신 “타입이 다르면 무조건 버린다”는 게 항상 최적은 아니라서 (실제로는 같은 위치에 재사용 가능한 DOM이었을 수도 있는데), 정확도를 약간 희생하고 속도를 얻는 트레이드오프다.

5. Fiber 리콘실리에이션 — 왜 새로 만들었나

리액트 15까지의 리콘실리에이션(Stack Reconciler)은 트리를 재귀 함수로 순회했다. 재귀는 한번 시작하면 스택이 다 풀릴 때까지 멈출 수 없다. 트리가 깊으면 이 동기 재귀가 메인 스레드를 오래 점유해서, 그 사이에 사용자 입력이나 애니메이션이 버벅였다.

리액트 16부터 도입된 Fiber는 트리 순회를 재귀에서 링크드 리스트 기반의 반복문으로 바꿨다. 각 컴포넌트마다 “Fiber 노드”라는 자바스크립트 객체를 만들고, 이 노드들이 child, sibling, return(부모) 포인터로 서로 연결된다.

FiberNode {
  type,       // 컴포넌트 타입
  key,
  child,      // 첫 번째 자식
  sibling,    // 다음 형제
  return,     // 부모
  memoizedState, // 훅 상태 저장 위치
  ...
}

이 구조 덕분에 순회 도중 어디까지 처리했는지를 Fiber 노드 자체에 기록해둘 수 있고, 브라우저가 “지금 처리할 일 남았어?”라고 물어보는 타이밍(requestIdleCallback 계열 스케줄러)마다 조금씩 순회하다가 중간에 멈추고 나중에 이어서 할 수 있다. 이게 앞서 말한 “렌더 페이즈는 중단 가능하다”의 실체다.

정리하면 Fiber는 알고리즘이라기보다 작업 단위(unit of work) 자료구조다. 이 자료구조가 있어서 우선순위 기반 스케줄링(사용자 입력을 애니메이션보다 먼저 처리한다든지)과 Concurrent 렌더링이 가능해졌다.

TypeScript 프로젝트에서의 참고

TS 프로젝트에서 Counter 같은 컴포넌트에 제네릭 props를 줄 때도 위 규칙은 그대로 적용된다. 특히 리스트 렌더링에서 key를 index로 주면 타입 에러는 안 나지만 런타임에서 state 꼬임이 생길 수 있으니, item.id처럼 안정적인 값에 타입을 명시해서 (key: string | number) 쓰는 습관을 들이면 좋다. 또한 조건부 훅 호출은 ESLint react-hooks/rules-of-hooks가 컴파일 타임이 아니라 린트 타임에 잡아주는 부분이라, TS의 타입 체크만 믿지 말고 이 규칙도 반드시 켜둬야 한다.
