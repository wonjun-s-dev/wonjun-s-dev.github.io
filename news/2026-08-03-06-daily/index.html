1. 초기 번들 사이즈가 너무 크다는 문제에서 시작

라우트가 20개쯤 되는 SPA를 한 번에 번들링하면, 사용자가 로그인 페이지만 보고 싶어도 관리자 대시보드, 통계 차트 라이브러리까지 전부 다운로드해야 한다. 이 문제를 코드 스플리팅으로 풀 때 쓰는 두 가지 도구가 레이지 로딩(React.lazy)과 Suspense다.

2. React.lazy — 컴포넌트를 동적 import로 감싸기

import { lazy } from "react";

const Dashboard = lazy(() => import("./Dashboard"));

lazy는 컴포넌트를 즉시 로드하지 않고, 실제로 렌더링이 필요한 시점에 동적 import()를 실행해서 그 순간에 코드를 네트워크로 받아온다. 번들러(webpack, Vite 등)는 import() 구문을 만나면 자동으로 해당 모듈을 별도의 청크(chunk) 파일로 분리한다. 결과적으로 초기 진입 시 받는 JS 번들에는 Dashboard 코드가 포함되지 않고, 사용자가 실제로 그 라우트에 진입할 때만 별도 파일이 다운로드된다.

function App() {
  const [page, setPage] = useState("home");
  return page === "dashboard" ? <Dashboard /> : <Home />;
}

문제는 import()가 비동기라는 것. Dashboard 모듈을 받아오는 동안 리액트가 렌더링할 게 없다. 이걸 그냥 두면 에러가 난다 — “A component suspended while rendering, but no fallback UI was specified.”

3. Suspense — 로딩 중 보여줄 화면을 선언

import { lazy, Suspense } from "react";

const Dashboard = lazy(() => import("./Dashboard"));

function App() {
  return (
    <Suspense fallback={<Spinner />}>
      <Dashboard />
    </Suspense>
  );
}

Suspense는 자식 트리 안에서 “아직 준비 안 됐다”는 신호(lazy 컴포넌트가 로딩 중이라는 것)를 감지하면, 그 트리를 통째로 fallback으로 대체해서 보여준다. Dashboard 모듈 다운로드가 끝나면 자동으로 fallback에서 실제 Dashboard로 전환된다.

여기서 중요한 개념은 “suspend(중단)”다. 컴포넌트가 렌더링 도중 아직 준비되지 않은 리소스(코드, 데이터)를 필요로 하면 에러를 던지는 대신 Promise를 던진다. 가장 가까운 상위 Suspense가 이 Promise를 붙잡아서 fallback을 보여주고, Promise가 resolve되면 그 지점부터 다시 렌더링을 시도한다. React.lazy는 이 메커니즘을 활용해서 “모듈 로딩 중”이라는 상태를 Suspense가 이해할 수 있는 형태로 만들어주는 래퍼다.

4. 여러 Suspense 경계의 배치 전략

function App() {
  return (
    <Suspense fallback={<PageSpinner />}>
      <Header />
      <Suspense fallback={<ChartSkeleton />}>
        <HeavyChart />
      </Suspense>
      <Footer />
    </Suspense>
  );
}

Suspense를 하나만 최상위에 두면, 트리 안 어디서든 뭔가 로딩 중이면 페이지 전체가 스피너로 바뀐다. 안쪽에 별도 Suspense를 두면 HeavyChart만 로딩 중일 때 Header/Footer는 이미 보여주고 그 부분만 스켈레톤으로 대체할 수 있다. 이걸 흔히 “Suspense 경계(boundary)를 세분화한다”고 한다 — 세분화할수록 사용자는 더 빨리 더 많은 UI를 보게 되지만, 스피너/스켈레톤이 여러 군데서 따로 나타나 화면이 산만해질 수 있으니 트레이드오프다.

5. 라우터와 결합했을 때의 실전 패턴

const Home = lazy(() => import("./pages/Home"));
const Dashboard = lazy(() => import("./pages/Dashboard"));
const Settings = lazy(() => import("./pages/Settings"));

function App() {
  return (
    <Suspense fallback={<PageSpinner />}>
      <Routes>
        <Route path="/" element={<Home />} />
        <Route path="/dashboard" element={<Dashboard />} />
        <Route path="/settings" element={<Settings />} />
      </Routes>
    </Suspense>
  );
}

라우트 단위로 lazy를 걸어두면, 각 라우트가 별도 청크로 분리되어 사용자가 방문한 라우트의 코드만 그때그때 받는다. 초기 로딩 시점엔 현재 라우트 하나만 다운로드하면 되므로 첫 화면 표시 속도(TTI, LCP)가 크게 개선된다. 실무에서 코드 스플리팅을 도입할 때 가장 먼저, 가장 효과가 큰 지점이 라우트 단위 분리다.

6. 흔히 하는 실수 — Suspense와 에러 처리를 혼동

Suspense는 “아직 준비 안 됨(로딩 중)”만 처리하고, “실패함(에러)”은 처리하지 않는다. import()가 네트워크 오류로 실패하면 Suspense가 아니라 에러 바운더리(Error Boundary)가 잡아야 한다.

<ErrorBoundary fallback={<LoadFailed />}>
  <Suspense fallback={<Spinner />}>
    <Dashboard />
  </Suspense>
</ErrorBoundary>

로딩 실패(청크 로드 실패는 배포 직후 캐시 문제로 실무에서 꽤 자주 발생한다)를 대비하려면 Suspense만 두지 말고 반드시 바깥에 에러 바운더리를 같이 둬야 한다.

정리 표

개념 역할 처리 대상
React.lazy 컴포넌트를 동적 import로 감싸 별도 청크 분리 코드 로딩
Suspense 자식이 준비 안 됐을 때 fallback UI로 대체 로딩 중 상태
ErrorBoundary 렌더링/로딩 중 발생한 에러 처리 실패 상태
Suspense 경계 세분화 부분별로 독립적인 로딩 표시 UX 세밀도 조절
라우트 단위 lazy 초기 번들 크기 축소 최초 로딩 성능

TypeScript 프로젝트에서의 참고

lazy(() => import("./Dashboard"))에서 Dashboard.tsx가 default export가 아니라 named export라면 타입 에러가 난다 (lazy는 { default: ComponentType } 형태의 Promise를 기대함). 이 경우 .then(module => ({ default: module.Dashboard }))처럼 래핑해야 하는데, 이 부분을 놓치는 경우가 흔하다. Vite/webpack에서 라우트별 청크 이름을 명시하고 싶다면 매직 코멘트(import(/* webpackChunkName: "dashboard" */ "./Dashboard"))를 쓰되, TS 컴파일러는 이 주석을 이해하지 못하므로 타입 체크와는 무관하게 번들러 설정 문서를 따로 참고해야 한다.
