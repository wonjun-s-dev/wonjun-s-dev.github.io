1. “useEffect가 왜 이 순서로 찍히지?” 에서 시작

여러 컴포넌트가 중첩된 트리에서 console.log를 각 useEffect와 useLayoutEffect에 넣어보면, 직관과 다른 순서로 로그가 찍힐 때가 있다. 오늘은 이 순서를 렌더 페이즈/커밋 페이즈 개념과 엮어서 정리했다.

2. useLayoutEffect vs useEffect — 실행 타이밍의 차이

function Box() {
  useLayoutEffect(() => {
    console.log("layoutEffect");
  });
  useEffect(() => {
    console.log("effect");
  });
  return <div>box</div>;
}

두 훅 다 “커밋 이후에 실행된다”는 공통점이 있지만, 브라우저 페인트와의 관계가 다르다.

  • useLayoutEffect: DOM 변경이 끝난 직후, 브라우저가 화면을 그리기 전에 동기적으로 실행된다. 이 안에서 DOM을 다시 읽고(측정) 조작해도 사용자는 중간 상태를 보지 못한다. 대신 여기서 무거운 작업을 하면 페인트가 그만큼 지연되어 화면이 버벅인다.
  • useEffect: 브라우저가 페인트를 마친 이후에 비동기적으로 실행된다. 화면은 이미 그려진 상태이므로, 여기서 DOM 크기를 재고 나서 state를 바꾸면 사용자 눈에 “깜빡임(flash)”이 보일 수 있다.
DOM 커밋 → useLayoutEffect (동기, 페인트 전) → 브라우저 페인트 → useEffect (비동기, 페인트 후)

그래서 “DOM 크기를 측정해서 즉시 레이아웃을 다시 잡아야 하는 경우”(툴팁 위치 계산 등)는 useLayoutEffect를 쓰고, “데이터 페칭, 구독 설정처럼 화면에 바로 영향을 안 주는 부수효과”는 useEffect를 쓰는 게 원칙이다.

3. 부모/자식 렌더링과 useEffect 실행 순서

function Parent() {
  console.log("Parent 렌더링");
  useEffect(() => {
    console.log("Parent useEffect");
  }, []);
  return <Child />;
}

function Child() {
  console.log("Child 렌더링");
  useEffect(() => {
    console.log("Child useEffect");
  }, []);
  return <div>child</div>;
}

이 코드의 실제 출력 순서는:

Parent 렌더링
Child 렌더링
Child useEffect
Parent useEffect

렌더링(함수 호출) 자체는 부모→자식 순서로 진행되지만, useEffect는 자식이 먼저, 부모가 나중이다. 직관적으로는 “위에서 아래로” 실행될 것 같은데 실제로는 반대다.

이유는 커밋 단계의 동작 방식에 있다. 리액트는 트리를 순회하면서 DOM을 실제로 붙이는데, 이 과정이 자식부터 완성되어야 부모에 붙일 수 있는 구조다(자식 DOM 노드가 먼저 만들어져야 부모가 그 자식을 담을 수 있으니까). 이펙트도 이 커밋 순서를 그대로 따라서, DOM 트리 상 가장 안쪽(리프에 가까운) 컴포넌트부터 이펙트가 실행되고 바깥쪽(부모)이 나중에 실행된다.

이 순서가 중요한 이유: 부모의 useEffect에서 자식이 만들어둔 DOM이나 자식의 이펙트 결과(ref로 노출된 값 등)에 의존하는 로직을 짜도 안전하다는 뜻이다. 자식의 이펙트가 이미 끝난 뒤에 부모 이펙트가 실행되기 때문이다.

cleanup은 반대 순서

언마운트될 때 cleanup 함수는 이펙트 실행의 역순으로, 이번엔 부모가 먼저, 자식이 나중이다.

Parent cleanup
Child cleanup

정확히는 “형제 컴포넌트 간에는 이전 형제부터, 부모-자식 간에는 부모의 cleanup이 자식보다 먼저” 실행된다. 마운트 때 자식 먼저 → 부모, 언마운트 때 부모 먼저 → 자식으로 대칭을 이룬다.

4. 형제 컴포넌트 간의 순서

function App() {
  return (
    <>
      <A />
      <B />
    </>
  );
}

A, B가 형제일 때는 JSX에 작성된 순서 그대로 A의 이펙트가 먼저, B의 이펙트가 나중에 실행된다. “자식 먼저, 부모 나중”이라는 depth 우선순위 규칙과, “형제는 작성 순서”라는 규칙이 합쳐져서 트리 전체의 이펙트 실행 순서가 결정된다.

정리하면 이펙트 실행 순서는 DOM 트리를 post-order(후위 순회)로 방문한 순서와 같다. 자식들을 먼저 방문(왼쪽부터 순서대로)하고, 그 다음 자기 자신을 방문하는 방식이다.

5. useLayoutEffect도 같은 순서 규칙을 따른다

useLayoutEffect와 useEffect는 실행 “타이밍”(페인트 전/후)만 다를 뿐, 트리 내에서의 상대적 순서 규칙(자식 먼저, 형제는 작성 순서)은 동일하다. 다만 useLayoutEffect는 페인트 전에 전체 트리의 layout effect가 다 끝나야 페인트가 진행되므로, 여러 컴포넌트에 useLayoutEffect가 있으면 페인트가 그만큼 늦어진다는 점을 기억해야 한다.

정리 표

상황 순서
렌더링(함수 호출) 부모 → 자식
useLayoutEffect / useEffect 실행 (마운트) 자식 → 부모 (post-order)
useLayoutEffect vs useEffect 타이밍 layoutEffect(페인트 전, 동기) → 페인트 → effect(페인트 후, 비동기)
cleanup 실행 (언마운트) 부모 → 자식
형제 컴포넌트 간 이펙트 순서 JSX 작성 순서대로

TypeScript 프로젝트에서의 참고

이펙트 순서에 의존하는 로직(부모가 자식 ref를 통해 값을 읽는다든지)을 짤 때는, TS의 useRef<HTMLDivElement>(null) 같은 타입을 정확히 잡아두면 “이 시점에 ref.current가 null일 수 있는가”를 컴파일러가 계속 경고해준다. 실제로 부모 useEffect에서 자식 ref를 읽는 경우, 마운트 첫 렌더 직후엔 ref.current가 채워져 있다는 걸 위 순서 규칙으로 보장할 수 있지만, 타입 상으로는 여전히 null 가능성이 남아있으니 옵셔널 체이닝이나 널 체크를 생략하지 않는 게 안전하다.
