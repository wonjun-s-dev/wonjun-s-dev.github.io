Created on August 03, 2026

2026   ·   React   Forms

1. input에 value를 줬는데 타이핑이 안 되는 버그

function SearchBox() {
  return <input value="검색어" />;
}

이 코드를 브라우저에서 실행하면 인풋에 아무리 타이핑을 해도 값이 바뀌지 않고, 콘솔에는 “You provided a value prop to a form field without an onChange handler” 경고가 뜬다. 이게 제어/비제어 컴포넌트 개념을 이해해야 하는 이유다.

2. 제어 컴포넌트 (Controlled Component)

function SearchBox() {
  const [value, setValue] = useState("");
  return (
    <input
      value={value}
      onChange={(e) => setValue(e.target.value)}
    />
  );
}

value를 리액트 state로 관리하고, 사용자가 타이핑할 때마다 onChange로 그 state를 갱신한다. 인풋에 실제로 보이는 값은 항상 리액트 state가 결정한다. 사용자가 타이핑을 해도, 브라우저 DOM이 자체적으로 값을 바꾸는 게 아니라 “이런 입력이 들어왔다”는 이벤트만 발생시키고, 그 이벤트를 받아 state를 바꾸면 리액트가 다시 그 state 값으로 인풋을 렌더링하는 식이다.

이 방식의 장점은 매 입력마다 값을 가로챌 수 있다는 것이다.

<input
  value={value}
  onChange={(e) => {
    const next = e.target.value.replace(/[^0-9]/g, ""); // 숫자만 허용
    setValue(next);
  }}
/>

입력값 검증, 실시간 포맷팅(전화번호 하이픈 자동 삽입 등), 다른 필드와의 동기화가 전부 onChange 한 곳에서 가능하다. 단점은 매 키 입력마다 리렌더링이 발생한다는 것 — 인풋이 많은 폼에서는 리렌더링 비용이 누적될 수 있다.

앞서 본 버그(value만 주고 onChange 없음)는 “제어 컴포넌트인데 값을 갱신할 방법이 없는” 상태라서 생긴다. 리액트는 value prop이 있으면 그 인풋을 제어 컴포넌트로 취급하고, DOM이 자체적으로 값을 바꾸는 걸 막아버리기 때문에 onChange 없이는 영원히 고정된 값만 보인다.

3. 비제어 컴포넌트 (Uncontrolled Component)

function SearchBox() {
  const inputRef = useRef(null);

  const handleSubmit = () => {
    console.log(inputRef.current.value); // 필요할 때만 DOM에서 직접 읽음
  };

  return (
    <>
      <input ref={inputRef} defaultValue="검색어" />
      <button onClick={handleSubmit}>검색</button>
    </>
  );
}

비제어 컴포넌트는 인풋의 값을 리액트 state가 아니라 DOM 자체가 들고 있게 둔다. 초기값은 value가 아니라 defaultValue로 주고(이후엔 리액트가 관여하지 않음), 값이 필요한 시점(제출 시 등)에 ref를 통해 DOM에서 직접 읽어온다.

장점은 매 키 입력마다 리렌더링이 일어나지 않는다는 것 — 브라우저 네이티브 인풋 동작 그대로라 성능 부담이 없다. 단점은 실시간 검증/포맷팅이 어렵다는 것(값이 바뀔 때마다 리액트가 알림을 받지 못하므로), 그리고 다른 state와 동기화하려면 결국 이벤트 리스너를 따로 붙여야 한다는 것.

4. 무엇을 기준으로 선택하나

기준 제어 비제어
매 입력마다 검증/포맷팅 필요 적합 부적합
다른 필드와 실시간 동기화 필요 적합 부적합
입력창이 매우 많은 대형 폼 (리렌더링 비용 민감) 리렌더링 비용 발생 리렌더링 없음, 유리
제출 시점에만 값이 필요 (단순 폼) 불필요한 복잡도 적합, 간단
서드파티 비제어 라이브러리(파일 업로드 등)와 통합 부적합 적합

실무에서는 대부분 제어 컴포넌트를 기본으로 쓰고(react-hook-form 같은 라이브러리는 사실 내부적으로 비제어 방식 + ref 구독을 써서 “제어 컴포넌트의 개발 경험 + 비제어의 성능”을 동시에 노리는 절충안이다), 성능이 정말 문제가 되는 대형 폼이나 파일 인풋(<input type="file">은 애초에 value를 코드로 못 바꾸므로 항상 비제어)에서만 비제어를 쓴다.

5. 하나의 인풋을 제어→비제어로, 혹은 그 반대로 바꾸면 생기는 문제

function Toggle() {
  const [showDefault, setShowDefault] = useState(false);
  return showDefault
    ? <input defaultValue="x" />      // 비제어
    : <input value="x" onChange={() => {}} />; // 제어
}

리액트는 한 인풋이 렌더링 도중 제어↔비제어로 전환되는 걸 경고한다(“component is changing an uncontrolled input to be controlled”). value가 undefined였다가 나중에 문자열이 되거나 그 반대인 경우 흔히 발생한다. 예방법은 초기 state를 절대 undefined로 두지 않고 항상 빈 문자열("")로 초기화해서, 처음부터 끝까지 “제어 컴포넌트”라는 정체성이 바뀌지 않게 하는 것이다.

const [value, setValue] = useState(""); // undefined 아님, 항상 제어 컴포넌트로 유지

TypeScript 프로젝트에서의 참고

제어 컴포넌트는 useState<string>("")처럼 제네릭을 명시해두면 onChange 핸들러의 e.target.value가 항상 string으로 추론되어 타입 불일치가 잘 안 생긴다. 비제어 컴포넌트는 useRef<HTMLInputElement>(null) 타입을 정확히 잡아야 inputRef.current.value 접근 시 current가 null일 수 있다는 걸 컴파일러가 강제로 체크해주니, inputRef.current?.value 형태의 옵셔널 체이닝을 습관화하는 게 좋다. react-hook-form + TS 조합에서는 register가 반환하는 타입이 곧 비제어 방식 ref 바인딩이라는 걸 알면, “왜 onChange를 직접 안 쓰는데도 값이 잡히지”라는 의문이 풀린다.
